# B03 representative village — implementation and verification

9 November 2026. **Partially implemented:** the representative village is locally playable and verified. Owner art/content review, physical Android/iPhone testing and G1/G2 acceptance remain open. The owner explicitly requested B03; this authorises the bounded implementation in the [prior plan](b03-village-plan.md), not final art approval or a passed release gate.

## What changed

The default proof now opens a compact village with four homes, a central lane, well square, provisions stall, olive trees, planted margins and an exit gate. David uses the existing B02 movement/camera components. Jesse, the provisions and the gate retain the same three guarded proof objectives. The well and houses are scenery, without new quests or interiors. The complete David and Goliath journey remains future work.

- [Village composition](../../scenes/world/village.tscn): editable placements, anchors, lighting and original imported gateway.
- [Reusable modules](../../scenes/world/village/): house, well, olive, stall and wall, built by [village_module.gd](../../scripts/world/village_module.gd).
- [Mesh builder](../../scripts/world/village_mesh.gd): one opaque vertex-colour mesh per generated module, separate simple colliders and a [shared material](../../assets/village/opaque_palette.tres). The existing GLB gateway remains unchanged.
- [World script](../../scripts/world/village.gd): ground, route surfaces, planting, distant silhouettes, gateway collision and the existing world-anchor API.
- [Village proof](../../scenes/proof/village_proof.tscn): composes the existing player, camera, character, input and UI. The shared proof controller accepts a world path, location label and build identity. The original courtyard remains an engine regression fixture.

Generated geometry is non-owned and guarded against duplicate setup. To inspect a changed module parameter, reopen/reinstantiate its scene; live parameter regeneration is not implemented. Module dimensions are authored values, not a general-purpose building editor. Changing a layout requires rerunning collision and exported journey checks.

## Layout and navigation

Coordinates use metres, Y up. Spawn is `(0, 0.1, 5)`, Jesse `(0, 0, 1.3)`, provisions `(3.2, 0, -0.7)` and the exit objective `(0, 0, -14)`. A 3.5 m central lane leads to the gate. The well has a public loop on the west; a perimeter route runs around all four homes. Visible walls bound X at ±14.5, south Z at 9.5 and north Z at -16.5. The arch can be traversed up to the outer boundary. The episode route beyond it is not implemented.

The actual David capsule was walked along every required approach, the well loop and the perimeter. A first route check found that the northeast home narrowed the northern passage too far; moving that home one metre south cleared the tested route. The stall counter is below the interaction ray so its solid geometry does not block the provision prompt. Camera-volume sampling found no solid overlaps on the tested routes. Sampling does not prove every possible camera pose.

## Cost, provenance and limitations

The complete static village world has **9,196 triangles, 40 mesh instances and 40 surfaces**, including the imported gateway and provision bundle, excluding characters, markers and UI. The 15,000-triangle / 70-surface assertion is a provisional engineering ceiling for this scene, not an owner-approved minimum-device budget. Runtime draw calls differ from static surface counts and are recorded in browser reports. No texture files, real-time shadows or new audio downloads were added.

All added geometry and colours are original local primitives, with provenance in [AP05](../assets/asset-register.md). This is a readable illustrated gameplay adaptation, not an archaeological reconstruction. Original GLB, WAV, Blender and DOCX fingerprints are preserved. ArrayMesh batching follows the [official Godot API](https://docs.godotengine.org/en/stable/classes/class_arraymesh.html).

Browser timing/FPS observations describe this Windows test host and automated sessions only. Touch emulation does not establish Android/iOS compatibility, thermal stability, camera comfort or minimum-device performance. Human clarity/enjoyment, final art, the full story, checkpoints across the complete episode and hosting remain unverified.
