# Production stack and visual quality review

**Test outcome.** The matched browser comparison now covers Godot, PlayCanvas and Unity 6.3 URP. It recommends PlayCanvas for production. The measurements, visual captures and port boundary are in the [stack comparison results](stack-comparison-results.md).

Decide the production stack and quality bar before planning scenes. For a lightweight, responsive 3D browser game, **PlayCanvas + TypeScript + Vite** is the first alternative I recommend evaluating against the current **Godot 4 + GDScript** build. Keep **Blender and GLB** as the shared character and animation pipeline. Use **WebGL 2** as the browser baseline, with WebGPU available as a separate enhancement test. The production engine decision remains open pending a matched comparison. [PlayCanvas standalone development](https://developer.playcanvas.com/user-manual/engine/standalone/) · [PlayCanvas browser support](https://developer.playcanvas.com/user-manual/engine/supported-browsers/) · [Godot web export](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)

## What modern game quality means here

| Area | What the exported browser build should demonstrate |
| --- | --- |
| Character animation | Clear weight shifts and foot contact during starts, stops and turns. Blends avoid visible pose jumps. Eye direction, brow and jaw movement read at close range. |
| Rendering | Skin, cloth and leather have distinct surface responses. Shadows anchor the character to the ground. The silhouette and face stay readable at gameplay distance and in close-ups, including in portrait. |
| Control and presentation | Keyboard and touch respond promptly. An authored animation and camera cue can run automatically, pause safely and return control without a camera snap or a second input. |
| Browser delivery | Track time to first control, compressed download size and frame pacing on the existing Intel N150 baseline. Use the existing provisional 30 FPS floor during sustained interaction. Check both orientations with emulated touch. |
| Production workflow | An animator can revise a clip or facial expression in Blender, reimport it and adjust a camera cue without rebuilding the controller. |

## What we know from the existing build

- The current village passed 38 Chrome checks covering its interaction, camera handoff, restart and responsive layout. That gives us working behaviors to preserve and retest. The older frozen Q06 build averaged 32 FPS over 15 minutes on the Intel N150. A separate startup retest reduced the cold median from **43.51 s to 9.41 s** over localhost using web-only vertex lighting. Character highlights darkened, and one trace still recorded a 7.60 s main-thread task. ## Original evaluation plan

1. **Prepare one neutral Blender sample.** Reuse David's rig and make one character with UV-mapped materials, a few facial shapes, walk and turn clips, and a short authored gesture. Export the same GLB for both engines. Use a plain floor and light so the comparison isolates animation, shading and delivery.
2. **Build the same test in both stacks.** Match camera paths, viewport and render resolution, lighting intent, and shadow coverage. Run Godot Compatibility with per-pixel lighting in an isolated test and keep the current web configuration as a reference. Compare both engines on WebGL 2. Use keyboard and emulated touch to start the cue once, pause it, and recover control. Time a clip update and a camera timing change in each stack.
3. **Collect side-by-side browser evidence.** Capture the same close-up and gameplay-distance motion. Run three launches in fresh Chrome processes and immediate reloads under the same conditions. Record compressed production transfer, time to first input, p95 frame interval, stalls and the sustained frame rate. Check portrait and landscape at a consistent quality setting. Emulation covers layout and input, and laptop figures describe laptop performance.
4. **Choose against the same bar.** Move to PlayCanvas if the matched export delivers the agreed look and controls within the browser budget, with a clear startup, frame pacing, visual or authoring advantage worth the runtime port. Keep Godot if it meets the same bar and the gain from switching is marginal. If both miss it, identify the shared asset or rendering bottleneck before investing in another runtime. Record the choice and port estimate before planning production scenes.
